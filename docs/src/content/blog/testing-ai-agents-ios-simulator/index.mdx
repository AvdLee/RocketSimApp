**Testing AI agents for the iOS Simulator** requires more than asking an agent to tap through an app once. A successful run can be luck, while a failed run can come from the model, the CLI, the Agent Skill, or the app itself. We wanted a repeatable way to tell those causes apart.

That is why we built AgentScenarios: a small, deterministic iOS app for testing and improving the [RocketSim CLI and Agent Skill](/docs/features/agentic-development/). It helps us reproduce difficult Simulator interactions, benchmark the complete command workflow, and turn every weakness into a scenario we can run again.

## Why agent testing needs scenarios

An agent usually follows a short loop: inspect the screen, choose a target, interact, wait for the UI to change, and inspect again. Each step looks simple until the app contains two buttons with the same label, a web view with sparse accessibility data, or an image that only makes sense visually.

Those are exactly the situations a happy-path demo skips. AgentScenarios deliberately includes them:

- Nested navigation with repeated row structures
- Duplicate button labels that require surrounding context
- A photo target that needs visual reasoning
- Sparse web content and native-to-web transitions
- Face ID prompts backed by `LocalAuthentication`
- Upside-down orientation and coordinate mapping
- A hidden debug menu that requires accessibility activation
- Swipe, long-press, text-entry, two-finger, and Home-button delivery
- Multi-step command batches that need to refresh screen state correctly

The app is intentionally local and deterministic. We can reset it before every run, start each tool from the same screen, and verify the result through visible state in the app. This gives us a much better signal than testing against a changing third-party app.

The scenarios also complement Apple's regular UI testing tools. Apple recommends preparing apps for automation with accessibility and writing stable, high-quality automation code in its [UI automation guidance](https://developer.apple.com/videos/play/wwdc2025/344/). RocketSim uses that same structured UI foundation, but exposes it to coding agents that need to inspect and control the app while working on your code.

## Testing the CLI and Agent Skill together

A CLI command can be correct while an agent still uses it incorrectly. The command surface and the instructions therefore need to be tested as one workflow.

The [RocketSim CLI](/docs/features/agentic-development/rocketsim-cli) provides compact element reads, semantic interactions, screen-change waits, screenshots, biometric controls, and setup diagnostics. The [RocketSim Agent Skill](/docs/features/agentic-development/agent-skill) explains when and how an agent should combine those commands.

For example, the skill encourages an agent to:

1. Read compact visible-element output
2. Prefer an element identifier or semantic selector
3. Include the current screen identifier when interacting
4. Wait for the screen to change
5. Read again before deciding on the next step
6. Fall back to a screenshot when accessibility data is not enough

You might wonder why the Agent Skill is part of the measurement if the CLI performs the actual interaction. The skill itself uses context, and its guidance can add or remove command turns. Our byte-based context estimate therefore includes the skill size, scenario prompt, and textual command output.

This setup also keeps RocketSim's CLI and Agent Skill version-matched. Both ship inside the RocketSim app, and their installed symlinks continue to point at the current version after an update. New commands and new guidance can evolve together instead of slowly drifting apart. For you as a developer, this means you only have to keep RocketSim updated to the latest App Store version. Your agents will automatically use the latest guidance and the best available way to interact with the Simulator.

## How we benchmark agent workflows

Our latest benchmark combines fifteen AgentScenarios flows with five workflows in the iOS Settings app. The fixture app covers nested navigation, duplicate labels, visual targets, web login, native-to-web transitions, hidden accessibility activation, Face ID, upside-down orientation, command batches, swipe, long-press, text entry, two-finger input, and Home-button delivery. The Settings scenarios add realistic scrolling, account entry, toggles, and stale-screen recovery.

Every comparable scenario ran three times in a single session against three pinned tools: RocketSim 16.4.2 build 326, [AXe](https://github.com/cameroncooke/AXe) 1.8.0, and [XcodeBuildMCP](https://github.com/cameroncooke/XcodeBuildMCP) 2.7.0, driven through its MCP server interface. The latest run, dated July 31st, contains **156 records in total**: **150 head-to-head tool/scenario records** and **six RocketSim-only capability records**.

One thing worth stating clearly, with credit to Cameron Cooke, the author of both AXe and XcodeBuildMCP, for this nuance: these two tools sit at different layers. AXe is deliberately a raw, non-agentic primitive layer. Returning the full accessibility tree is a design choice, not a flaw, and it leaves filtering to whatever builds on top of it. XcodeBuildMCP is such a layer: it builds on AXe and adds state management and compact output. That compact output follows the approach of [`rs/1`, the agent protocol we designed for RocketSim](/docs/features/agentic-development/rs1-protocol/). Cameron mentioned to me that the rs/1 approach was a good direction that he also incorporated into XcodeBuildMCP. I consider that a great validation of the design. Keep these layers in mind when reading the multipliers below.

Not every scenario could run on every tool. Face ID and two-finger input remain RocketSim-only capability records because neither AXe 1.8.0 nor XcodeBuildMCP 2.7.0 offers equivalent commands. XcodeBuildMCP 2.7.0 also sat out the web login, hybrid web, cross-screen batch, and coordinate swipe scenarios: its runtime snapshot does not expose WKWebView content, it has no coordinate tap or swipe fallback, and its batch command only accepts same-screen steps. Those scenarios stay head-to-head between RocketSim and AXe.

The runner uses dedicated Simulators, pins the tested tools and Agent Skills by version and SHA-256, automates AgentScenarios setup, and scopes orientation and biometric state to the selected device. This run used RocketSim 16.4.2 build 326, Xcode 26.6, iOS 26.5, and macOS 26.5.2. It separates comparable scenarios from capability-only checks and records timing distributions instead of relying on a single run.

For each scenario, we record:

- Command turns
- Standard output and error bytes
- A byte-based context estimate
- Total elapsed time
- Wrong taps
- Unexpected failures

The byte-based context estimate includes the skill, prompt, and textual command output. For XcodeBuildMCP, it charges the MCP tool catalog once per scenario, symmetric with how the skill files are counted for the CLI tools. It is a reproducible comparison proxy rather than actual model-token or billing usage. Screenshots are stored as artifacts, but their binary file contents are not included.

The scenario scripts are frozen, and so are the results. When current iOS 26 Settings UI drift makes a step fail, that failure stays in the recorded results for every tool instead of being normalized away.

Freezing the scenarios makes the comparison repeatable, but it also means this is a benchmark of the agent substrate rather than a ranking of AI models. Fixed drivers execute documented command patterns, so the run measures the tools and their recommended workflows without measuring an LLM's reasoning quality. Model choice, context, caching, and decision-making can still change the result of a real coding session.

## What the benchmark taught us

The most important results are not the byte multipliers, but correctness and capability coverage. RocketSim completed every scenario type in the run, including Face ID, two-finger input, web login, cross-screen command batches, and coordinate swipes. AXe 1.8.0 covered everything except Face ID and two-finger input. XcodeBuildMCP 2.7.0 ran fourteen of the twenty scenarios head-to-head, sitting out the six described above.

No tool had a perfect run, including ours. RocketSim recorded **seven wrong interactions and one unexpected failure**: six wrong interactions came from the frozen Settings scripts, and the Face ID scenario recorded one wrong interaction and one unexpected failure in round three. AXe recorded fifteen wrong interactions and XcodeBuildMCP nine. Almost all of them, across all three tools, came from the frozen Settings scripts hitting current iOS 26 UI drift. XcodeBuildMCP additionally tapped through a stale element reference in the stale-navigation scenario in all three rounds, where RocketSim recovered. We keep those failures visible instead of normalizing the scripts until every run passes.

On efficiency, the largest multipliers come from the raw AXe comparison. Against AXe 1.8.0, the frozen run shows **119.3× fewer output bytes**, a 21.0× lower byte-based context estimate, and 66.5 seconds less total command time. That still rounds to over 99% less command output and about a 95% lower context proxy, but it is a comparison against a primitive layer that returns the full accessibility tree on purpose.

The XcodeBuildMCP comparison is the fairer one, because its compact output builds on the same rs/1 approach that RocketSim introduced. Over the fourteen scenarios both tools ran head-to-head, XcodeBuildMCP produced **3.0× RocketSim's tool-response bytes**, an **8.2× higher byte-based context estimate** (which charges its MCP tool catalog once per scenario, exactly like the skill files for the CLI tools), and finished **171.5 seconds slower** in total. RocketSim used more command turns to get there: XcodeBuildMCP needed 0.79× as many turns, and AXe 0.70×.

Those numbers still support the design behind [`rs/1`](/docs/features/agentic-development/rs1-protocol/), the compact agent protocol we designed for RocketSim. Seeing other tools adopt the same approach confirms the direction, and this benchmark shows the original implementation still leads. An agent usually does not need a full accessibility tree for every step. It needs enough information to identify the target, interact safely, and verify what changed.

We consider that result valuable. A benchmark should reveal what to improve, not just produce a marketing number. Comparing the latest run with our earlier baseline shows how measured weaknesses can turn into product improvements:

- Face ID interactions now provide reliable completion notifications
- Accessibility failures return typed, actionable errors
- Multi-step command batches can start without requiring a seeded snapshot
- Refresh failures remain correctly wrapped in the agent protocol response

The latest harness also automates hidden debug-menu activation, upside-down orientation, swipe, long-press, text entry, two-finger input, and Home-button checks. Face ID and two-finger input remain RocketSim-only capability scenarios because neither AXe 1.8.0 nor XcodeBuildMCP 2.7.0 offers equivalent commands. Whenever the CLI or Agent Skill changes, these focused scenarios make it easier to verify the behavior that motivated the change. And to be fair to ourselves too: the Face ID failure in round three is exactly the kind of weakness the next iteration should turn into a fix.

## November 2026 update: a faster CLI

After the July run, we spent our time on speed. An agent waits on every call, so a faster tap and a smaller answer add up over a long flow. Four changes did most of the work:

- Actions now settle by watching the Simulator's pixels, so RocketSim reads the screen again as soon as it stands still instead of after a fixed wait.
- Focusing a field and typing into it is one call, and the text goes out over the connection that taps already use.
- Answers carry less: rows drop columns that never change, scroll indicators and keyboard keys stay out of compact snapshots, and the JSON envelope is gone: reading the screen, tapping and batching now answer in a few plain lines.
- RocketSim skips redundant accessibility reads when the top of the screen has not changed.

### On the public simulator-use benchmark

[simulator-use](https://simulator-use.dev/benchmarks) publishes an open-source harness and a leaderboard that signs in to the same app with nine tools, each driven the way its README describes. We ran RocketSim through the same harness. These are the numbers for the RocketSim 17.0 pre-release, next to the nine tools on the page:

| Measure                          | RocketSim | Where it lands among the ten tools                                                                                                                                                   |
| -------------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Tokens read over a whole sign-in | 164       | The lowest of the ten tools. The next lowest, simulator-use, reads 194.                                                                                                              |
| Whole sign-in, step by step      | 3.00 s    | Second fastest. Only ios-simulator-mcp is quicker (2.08 s), and it reads 5,248 tokens to get there.                                                                                  |
| Tap Sign In                      | 0.49 s    | Faster than simulator-use on the same Mac (0.53 s), and the answer shows what the tap did. ios-simulator-mcp taps in 0.20 s but never shows the result, and 2 of its 20 taps missed. |
| Type into a field                | 1.37 s    | In the middle of the field (it runs from 0.41 s to 4.06 s).                                                                                                                          |
| Read the screen                  | 0.26 s    | Seventh of ten (the field runs from 0.08 s to 1.52 s).                                                                                                                               |

Every step worked in every run. The earlier run on 18 November took 1.17 seconds for a tap and 5.7 seconds for the sign-in.

Two things to keep in mind. The page's times come from its author's Mac and ours from a cloud Mac, so we also ran the harness next to simulator-use 0.15.3 on the same Mac in the same session. RocketSim read fewer tokens in every measure there (164 against 194 for the sign-in, 51 against 72 for a read, 165 against 179 for the batched sign-in) and tapped faster (489 and 497 ms against 533 ms). simulator-use was faster at reading (234 ms against 260 ms), typing (930 ms against 1.37 s) and the whole sign-in (2.79 s against 3.00 s). Tokens are the benchmark author's estimate (characters divided by four).

### In our own scenarios

We also reran our own scenarios on an isolated Mac with iOS 27.2: the sixteen AgentScenarios flows plus the five Settings flows, three rounds, RocketSim against XcodeBuildMCP 2.7.0.

- RocketSim completed **47 of the 48 runs of the sixteen fixture flows without a wrong tap or a failure**; the one exception was a first run after a Simulator reboot that passed in both repeats. XcodeBuildMCP, which can run nine of them, finished 23 of its 27 runs, with wrong taps in the stateful text-entry and press-Home flows in two of three rounds each.
- Across the scenarios both tools ran, RocketSim produced 4.3 times fewer tool-response bytes and a 9.7 times lower context estimate, and finished 1.7 times faster in total. XcodeBuildMCP needed fewer commands (0.75 times as many turns).
- The Settings flows still fail for both tools, because our frozen scripts meet the iOS 27.2 Settings app: RocketSim passed 10 of 15 runs and XcodeBuildMCP 7 of 15. We keep those failures in the record.

The Simulator's accessibility service stopped answering twice during long runs in which both tools shared a Simulator, until we rebooted it, so we rebooted before each group of scenarios and ran the last round one tool at a time. We do not yet know what triggers it. The full run, scripts and logs are in our repository's evaluation notes.

## Why this matters for agentic iOS development

Agentic development becomes useful when an agent can close the feedback loop. Editing Swift code is only half the work; the agent should also navigate to the changed screen and verify the result in the iOS Simulator.

Reliability matters more as those flows become longer. One wrong tap near the start of onboarding can invalidate every step after it. Oversized element output can fill the context window before the agent reaches the screen it needs. A missing wait can make a correct interaction look like a failure.

RocketSim's [agentic iOS Simulator development tools](/features/agentic-development) are built around these constraints. The running Mac app keeps Simulator state warm, the CLI exposes a compact interaction layer, and the Agent Skill teaches coding tools how to use that layer consistently.

Testing all three parts against repeatable scenarios gives us confidence that an improvement works beyond a single demo. It also keeps the product honest: if a richer response costs too many tokens or a faster interaction causes more wrong taps, the benchmark makes that trade-off visible. If you want a practical introduction first, read [AI agents for the iOS Simulator](/blog/ai-agents-ios-simulator/), or see how you can [follow an agent live in Browser Preview](/blog/ios-simulator-browser-preview/). If you are deciding between an MCP server and a CLI with an Agent Skill, [iOS Simulator MCP vs CLI and Agent Skill](/blog/ios-simulator-mcp/) explains how to choose.

## Conclusion

Testing AI agents for the iOS Simulator works best with small, repeatable scenarios and measurements that cover more than success or failure. AgentScenarios lets us measure output size, byte-based context estimates, elapsed time, and wrong interactions while continuously expanding our regression coverage.

If you want your coding agent to inspect and navigate a running app, install [RocketSim from the Mac App Store](https://apps.apple.com/app/apple-store/id1504940162?pt=117264678&ct=testing-ai-agents-ios-simulator&mt=8), then open **RocketSim → Settings → CLI & Agent** to install the CLI and Agent Skill.
