**Testing AI agents for the iOS Simulator** requires more than asking an agent to tap through an app once. A successful run can be luck, while a failed run can come from the model, the CLI, the Agent Skill, or the app itself. We wanted a repeatable way to tell those causes apart.

That is why we built AgentScenarios: a small, deterministic iOS app for testing and improving the [RocketSim CLI and Agent Skill](/docs/features/agentic-development/). It helps us reproduce difficult Simulator interactions, benchmark the complete command workflow, and turn every weakness into a scenario we can run again.

## Why agent testing needs scenarios

An agent usually follows a short loop: inspect the screen, choose a target, interact, wait for the UI to change, and inspect again. Each step looks simple until the app contains two buttons with the same label, a web view with sparse accessibility data, or an image that only makes sense visually.

Those are exactly the situations a happy-path demo skips. AgentScenarios deliberately includes them:

- Nested navigation with repeated row structures
- Duplicate button labels that require surrounding context
- A photo target that needs visual reasoning
- Sparse web content and native-to-web transitions
- Face ID prompts backed by `LocalAuthentication`
- Upside-down orientation and coordinate mapping
- A hidden debug menu that requires accessibility activation
- Swipe, long-press, text-entry, two-finger, and Home-button delivery
- Multi-step command batches that need to refresh screen state correctly

The app is intentionally local and deterministic. We can reset it before every run, start each tool from the same screen, and verify the result through visible state in the app. This gives us a much better signal than testing against a changing third-party app.

The scenarios also complement Apple's regular UI testing tools. Apple recommends preparing apps for automation with accessibility and writing stable, high-quality automation code in its [UI automation guidance](https://developer.apple.com/videos/play/wwdc2025/344/). RocketSim uses that same structured UI foundation, but exposes it to coding agents that need to inspect and control the app while working on your code.

## Testing the CLI and Agent Skill together

A CLI command can be correct while an agent still uses it incorrectly. The command surface and the instructions therefore need to be tested as one workflow.

The [RocketSim CLI](/docs/features/agentic-development/rocketsim-cli) provides compact element reads, semantic interactions, screen-change waits, screenshots, biometric controls, and setup diagnostics. The [RocketSim Agent Skill](/docs/features/agentic-development/agent-skill) explains when and how an agent should combine those commands.

For example, the skill encourages an agent to:

1. Read compact visible-element output
2. Prefer an element identifier or semantic selector
3. Include the current screen identifier when interacting
4. Wait for the screen to change
5. Read again before deciding on the next step
6. Fall back to a screenshot when accessibility data is not enough

You might wonder why the Agent Skill is part of the measurement if the CLI performs the actual interaction. The skill itself uses context, and its guidance can add or remove command turns. Our byte-based context estimate therefore includes the skill size, scenario prompt, and textual command output.

This setup also keeps RocketSim's CLI and Agent Skill version-matched. Both ship inside the RocketSim app, and their installed symlinks continue to point at the current version after an update. New commands and new guidance can evolve together instead of slowly drifting apart. For you as a developer, this means you only have to keep RocketSim updated to the latest App Store version. Your agents will automatically use the latest guidance and the best available way to interact with the Simulator.

## How we benchmark agent workflows

We use two kinds of measurements, both from November 2026 and both on the same RocketSim 17.0 pre-release build. The first is the public simulator-use benchmark, which tells us how RocketSim compares with other tools on the same task. The second is our own scenarios, which measure whether RocketSim handles harder interactions correctly.

### The public simulator-use benchmark (November 2026)

The simulator-use project publishes a public, open-source benchmark for iOS Simulator tools: a [leaderboard](https://simulator-use.dev/benchmarks) and the [harness behind it](https://github.com/NoMac-app/simulator-use/tree/main/bench), which signs in to the same demo app with nine tools, each driven the way its own README describes. We did not design it and it is not ours: we ran RocketSim through the project's own, unmodified harness, so the numbers are measured the same way as every other tool on the page. This is our own run, not an entry the project has published. Here is where RocketSim lands:

- **Tokens:** the lowest of the ten tools. The next lowest, simulator-use, reads 194.
- **Whole sign-in:** second fastest. Only ios-simulator-mcp is quicker (2.08 s), and it reads 5,248 tokens to get there.
- **Tap:** 0.49 s, faster than simulator-use on the same Mac (0.53 s), and the answer shows what the tap did. ios-simulator-mcp taps in 0.20 s but never shows the result, and 2 of its 20 taps missed.
- **Type:** in the middle of the field, which runs from 0.41 s to 4.06 s.
- **Read:** seventh of ten, in a field that runs from 0.08 s to 1.52 s.

Every step worked in every run.

Two things to keep in mind. The page's times come from its author's Mac and ours from a cloud Mac, so we also ran the harness next to simulator-use 0.15.3 on the same Mac in the same session. RocketSim read fewer tokens in every measure there (164 against 194 for the sign-in, 51 against 72 for a read, 165 against 179 for the batched sign-in) and tapped faster (489 and 497 ms against 533 ms). simulator-use was faster at reading (234 ms against 260 ms), typing (930 ms against 1.37 s) and the whole sign-in (2.79 s against 3.00 s). Tokens are the benchmark author's estimate (characters divided by four) and do not depend on the Mac; times do.

#### How we ran it

- **Harness:** `NoMac-app/simulator-use` at commit `d75ef5e`, `bench/run.mjs` and `bench/summarize.mjs`, unchanged. The only addition is a RocketSim adapter in `bench/tools/`, written the way the other adapters are.
- **Machine:** one fresh cloud Mac ([NoMac](https://nomac.app), macOS 26.6.2, Xcode 27.2), a new iPhone 17 Pro Simulator on iOS 27.2 and the harness's demo app, with nothing else running.
- **Tools:** the RocketSim 17.0 pre-release build (Pro licence, started headless) and simulator-use 0.15.3, the version preinstalled on that Mac, both on the same Mac in the same session. RocketSim ran twice and simulator-use once, and simulator-use ran last because the Simulator's accessibility service sometimes stops answering after it.
- **Samples:** medians of 20 reads, 20 taps, 10 typings, 10 step-by-step sign-ins and 10 batched sign-ins.
- **How RocketSim is driven:** RocketSim has no MCP server, so each step is one `rocketsim` command, timed from spawn to exit, and what it prints is what the agent reads. Reads, taps and typing go by accessibility identifier, as RocketSim's bundled Agent Skill advises, and the batched sign-in is one `do` call.
- **What we publish:** the adapter, the harness's own result files and the steps to repeat the run are in [our repository](https://github.com/AvdLee/RocketSimApp/tree/master/Benchmarks/simulator-use). If you reproduce it and get different numbers, tell us.

### Our own scenarios: AgentScenarios

The public benchmark signs in to one demo app, so it says little about harder interactions. To measure how reliably RocketSim handles those, we run AgentScenarios: sixteen fixture flows and five workflows in the iOS Settings app, three rounds each, on an isolated Mac with iOS 27.2. The fixture app covers nested navigation, duplicate labels, visual targets, web login, native-to-web transitions, hidden accessibility activation, Face ID, upside-down orientation, command batches, swipe, long-press, text entry, two-finger input, and Home-button delivery. The Settings scenarios add realistic scrolling, account entry, toggles, and stale-screen recovery.

The runner uses dedicated Simulators, pins the Agent Skill by SHA-256, and reboots the Simulator before each group of scenarios. For each scenario, we record command turns, output bytes, a byte-based context estimate (the skill, the prompt, and the textual command output; screenshots are stored as artifacts but their contents are not counted), elapsed time, wrong taps, and unexpected failures.

- RocketSim completed **47 of the 48 runs of the sixteen fixture flows without a wrong tap or a failure**, including Face ID, two-finger input, web login, cross-screen command batches, and coordinate swipes. The one exception was the first run after a Simulator reboot, which passed in both repeats.
- The Settings flows are the weak spot: 11 of 15 runs were clean. The Apple Account sign-in flow fails in every round because our frozen script meets the iOS 27.2 Settings app, and we keep that failure in the record instead of editing the script until it passes.

The scenario scripts are frozen, and so are the results. Freezing them makes the comparison repeatable, but it also means this is a benchmark of the agent substrate rather than a ranking of AI models. Fixed drivers execute documented command patterns, so the run measures the tools and their recommended workflows without measuring an LLM's reasoning quality. Model choice, context, caching, and decision-making can still change the result of a real coding session.

## What the benchmark taught us

Our goal is the most reliable and most efficient CLI for agents, not the fastest single command. The numbers show that choice. RocketSim reads the fewest tokens of the ten tools and taps in 0.49 s, and on the same Mac it is a little slower than simulator-use at reading, typing and the whole sign-in.

We accept that trade because a command's duration is only part of what an agent spends. A fast command that returns too little leaves the agent guessing: it reads again, taps again or recovers from a miss, and every extra round trip costs tokens and a model turn that takes seconds, far more than the few hundred milliseconds between two commands. The benchmark times commands rather than model turns, so it does not show that effect directly, but the public data points the same way:

- **Taps that report what happened:** the tap answers of four of the eight other tools in the table never say what changed (0 of 20 for mobile-mcp, Maestro MCP and MobileBuildMCP, and 0 of 18 for ios-simulator-mcp). RocketSim's answer to a tap is the screen it landed on and what appeared, so the agent can move on without a read.
- **Taps that land:** every RocketSim step worked in every run, 20 of 20 taps and 10 of 10 sign-ins. ios-simulator-mcp is the fastest tapper at 0.20 s, but 2 of its 20 taps missed.
- **Answers an agent can act on:** RocketSim answers a screen read, a tap, or a batch in a few plain lines, without a JSON wrapper, and its command line adds nothing to the agent's context before the first action (simulator-use's tool list costs 2,443 tokens). That is what the [`rs/1`](/docs/features/agentic-development/rs1-protocol/) protocol is for: an agent usually does not need a full accessibility tree for every step. It needs enough information to identify the target, interact safely, and verify what changed.
- **Hard interactions:** the scenarios above cover cases a demo sign-in never reaches, such as Face ID, two-finger input, web login and cross-screen batches, and RocketSim completed 47 of the 48 fixture-flow runs cleanly.

A benchmark should reveal what to improve, not just produce a marketing number. This one shaped how we made reading, tapping and typing faster and smaller, and we re-ran our own scenarios after every change to check that nothing broke. The Simulator's accessibility service stopped answering in some long runs until we rebooted it, so we reboot before each group of scenarios.

## Why this matters for agentic iOS development

Agentic development becomes useful when an agent can close the feedback loop. Editing Swift code is only half the work; the agent should also navigate to the changed screen and verify the result in the iOS Simulator.

Reliability matters more as those flows become longer. One wrong tap near the start of onboarding can invalidate every step after it. Oversized element output can fill the context window before the agent reaches the screen it needs. A missing wait can make a correct interaction look like a failure.

RocketSim's [agentic iOS Simulator development tools](/features/agentic-development) are built around these constraints. The running Mac app keeps Simulator state warm, the CLI exposes a compact interaction layer, and the Agent Skill teaches coding tools how to use that layer consistently.

Testing all three parts against repeatable scenarios gives us confidence that an improvement works beyond a single demo. It also keeps the product honest: if a richer response costs too many tokens or a faster interaction causes more wrong taps, the benchmark makes that trade-off visible. If you want a practical introduction first, read [AI agents for the iOS Simulator](/blog/ai-agents-ios-simulator/), or see how you can [follow an agent live in Browser Preview](/blog/ios-simulator-browser-preview/). If you are deciding between an MCP server and a CLI with an Agent Skill, [iOS Simulator MCP vs CLI and Agent Skill](/blog/ios-simulator-mcp/) explains how to choose.

## Conclusion

Testing AI agents for the iOS Simulator works best with small, repeatable scenarios and measurements that cover more than success or failure. AgentScenarios lets us measure output size, byte-based context estimates, elapsed time, and wrong interactions while continuously expanding our regression coverage.

If you want your coding agent to inspect and navigate a running app, install [RocketSim from the Mac App Store](https://apps.apple.com/app/apple-store/id1504940162?pt=117264678&ct=testing-ai-agents-ios-simulator&mt=8), then open **RocketSim → Settings → CLI & Agent** to install the CLI and Agent Skill.
